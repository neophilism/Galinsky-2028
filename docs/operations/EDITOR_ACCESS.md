# Campaign editor entry and authorization (17 October 2026)

The existing database-backed campaign content editor is under `/editor/campaigns` on the **existing password-protected volunteer portal**, not a new site or server. When `G28_CAMPAIGN_EDITOR_ENABLED=true`, the existing admin verified-email flow is operational and the protected database is configured, a signed-in **owner or editor** sees a direct **Campaign content editor** navigation link. The regular volunteer, auditor and treasurer never see that link.

**Security correction:** The editor's HTML, JavaScript and CSS were previously served to anyone inside the shared preview password gate when the feature flag was on, even though all editorial APIs already required a fresh owner/editor session. They now require that same freshly checked role to view the editor shell or scripts. This is defense in depth: source code itself is not considered secret, but an editorial UI should not advertise private functionality to an unprivileged session. Shared preview credentials alone never confer editorial access. Content APIs remain strictly authorized and CSRF-checked for mutations; publication remains owner-only.

Feature visibility does **not** grant staff access, enable sender delivery, publish a campaign, or bypass any security gate. The flag is false if the admin login, explicit editor feature or database configuration is absent. Actual deployment must still verify sender, owner email, staff grants, database reader isolation, preview authentication and real browser edit/publish/rollback. No names or campaign variants are committed to Git; database editorial content remains private.

Tests: `tests/integration/campaign-routes.test.mjs` verifies anonymous 401, prohibited-role 403, disabled-feature 503 and owner 200 for all editor shell resources. `tests/inline-mail-release.test.mjs` verifies the navigation feature flag is enabled only with explicit authorization-relevant configuration. This does not complete G28-20/37/66/71.
