# Mail delivery, notices and suppression

The existing Resend sender and leased outbox now support fixed transactional welcome and security notices, plus consented workspace reminders. A first verified public account commits one welcome with its session; retries cannot create extra welcomes. Passkey enrollment/revocation commit generic encrypted security notices in the same transaction as the device change. The internal `queueAccountNotice` helper accepts only fixed kinds and stable event keys; reminder dispatch rechecks current optional consent. It is not a bulk-mail composer. No protected report, device label, recovery key, campaign persuasion text or arbitrary task narrative is put in mail. Envelope payloads are erased on terminal completion; stable provider IDs survive for delivery correlation. A Resend acceptance ID means accepted for processing, not confirmed mailbox delivery.

The authenticated callback route is `POST /api/mail/events`. It verifies exact raw bytes with pinned Svix, including timestamp tolerance, before parsing. Signed event identity and body digest make replays idempotent and conflicting replays fail. Only the configured delivery event types are accepted. Mail acceptance and callbacks serialize by provider message ID, including callbacks that arrive before the acceptance record. Hard bounce, complaint and provider suppression records block later sends; transient delays/bounces do not fabricate permanent suppression. Optional consent withdrawal also stops reminders. Only provider IDs, event kind/digest and HMAC subject identifiers are retained, never callback recipient arrays or subject/body. Callback metadata expires after 90 days; suppression stays until an authorized deliverability/privacy lifecycle decision so account deletion cannot resubscribe a complained address.

Set `RESEND_WEBHOOK_SECRET` as a portal service secret from the [Resend webhook settings](https://resend.com/webhooks). Select `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.complained`, `email.failed` and `email.suppressed`. Follow [Resend's raw-signature guidance](https://resend.com/docs/webhooks/verify-webhooks-requests). Existing sender and API credentials are reused; no replacement API key is required by this change.

The current private preview Basic password is still required at this route. The route exempts only the exact callback URL from browser Origin/CSRF rules; it does not bypass preview authentication. Configure an approved private authenticated callback delivery path before expecting provider callbacks to reach the preview. Do not put the preview password in a webhook URL, publish an unauthenticated preview exception, or claim real callback delivery from synthetic tests. Public launch and callback ingress remain explicit release configuration. The existing sign-in worker can keep operating while that ingress is private.

Tests exercise actual HTTP signatures, byte changes, stale timestamps, replay conflicts, preview authentication, consent rechecks, no-send suppression, fixed templates, redacted logs and real PostgreSQL acceptance/callback races. No real recipient messages are sent by those tests. A deployed real-mailbox journey still requires observation before public registration opens.
