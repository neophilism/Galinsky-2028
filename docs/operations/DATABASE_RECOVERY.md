# Database recovery

The recovery operator is the repository owner or a separately appointed database operator. `scripts/database-recovery.mjs` creates authenticated AES-256-GCM encrypted, consistent PostgreSQL custom archives. It never accepts private recipient keys as a server recovery shortcut. Keep the random 32-byte base64 recovery key in an owner-controlled secret manager, separately from archives, application secrets and repository contents. Record its printed key identifier and retain old keys for the lifespan of their generations. Losing a key makes that generation unrecoverable.

Use a PostgreSQL client version compatible with the source server. Set `DATABASE_URL` and `RECOVERY_KEY_BASE64` through the operator's private environment. Run `node scripts/database-recovery.mjs backup /private/path/generation.g28`. The file is created exclusively with owner-only permissions; an existing generation is never overwritten. Copy the encrypted archive and redacted success JSON to the approved private backup store. Do not place either production archives or plaintext dumps in GitHub/CI artifacts. Record the repository commit, database branch, generation creation time, key identifier and destination inventory in the private operator log. Database-stored content, media and object manifests are included. Git-tracked public assets are rebuilt from that exact repository commit. Any separately stored blobs need their matching inventory and separately authorized recovery material; this command does not invent missing object backups.

Restore into a new, empty, isolated database named `g28_restore_<unique_suffix>`. Set `RESTORE_DATABASE_URL`, `RESTORE_CONFIRM_DATABASE` to its exact database name, and the generation's `RECOVERY_KEY_BASE64`. Run `node scripts/database-recovery.mjs restore /private/path/generation.g28`. The complete archive is authenticated before SQL runs. It rejects source reuse, nonempty targets, wrong keys and altered archives. Restore runs in one PostgreSQL transaction. Temporary plaintext is owner-only inside a private directory and removed on success/failure; use encrypted operator disks and an isolated host. Access to the backup/key confers database recovery authority, so never restore an untrusted archive.

Ownership is intentionally omitted during restore. Original ACLs, including function revocations, are preserved. Provision the original separately scoped role names on the target cluster before recovery; missing roles make the transaction fail. Recheck the public projection and visitor-ingest grants documented in `CAMPAIGN_CONTENT_HANDOFF.md` and `VISITOR_ANALYTICS.md` before connecting any application. The recovery operator remains the initial database owner. Confirm public-reader roles cannot read account, editorial draft, staff, finance or protected tables. Keep all recovered workers and outbound providers disabled until duplicate delivery/provider replay reconciliation is complete. Retain login/outbox expiry and idempotency checks; do not blindly resend accepted deliveries or retry uncertain charges. Replay only authenticated provider events with their existing event IDs through the tested ledger, then reconcile provider records and deposits. Rebuild public content from the recorded Git commit and verify material/media hashes. Apply legal-hold/deletion tombstones accumulated since the snapshot before exposing a recovered database. Never reactivate a closed account from a stale backup.

`tests/integration/database-recovery.test.mjs` runs the real tools against synthetic local PostgreSQL databases, restores all migrations and content, measures backup/restore times, and checks altered archives, wrong keys, source reuse and nonempty-target rejection. GitHub CI retains the measured synthetic result in its job log. This is implementation proof, not a measured production RPO/RTO. Before production activation, inspect the actual Neon tier/retention, authorize private archive storage and a generation schedule, record recovery owners, and rehearse the exact production-sized isolated recovery. Starting goals of RPO ≤24 hours and RTO ≤4 hours require those observations; no paid backup tier or background schedule is created by this script.
